# План архитектуры BitRate

Этот документ описывает целевую реализацию; сейчас готов только каркас.

## Ресурсы

- **Project**: UUID, название, описание, время создания/обновления.
- **Audit**: UUID, project_id, тип `code` или `design`, версия правил,
  время создания и первоначальная оценка 0–100.
- **Finding**: UUID, audit_id, идентификатор правила, описание, рекомендация,
  severity (`low`, `medium`, `high`, `critical`), status (`open`, `resolved`),
  комментарий о решении.

Связи: Project 1 → N Audit; Audit 1 → N Finding.
Отчёт вычисляется из аудита и связанных проблем, отдельно не хранится.
Оценки кода и дизайна не объединяются в один балл.

## Три содержательных сценария

### 1. Управление проектом и его историей

Создать проект, изменить метаданные, просмотреть историю аудитов, удалить проект.
Название после удаления пробелов должно быть длиной 1–100 символов;
описание — до 2000. Имена уникальны без учёта регистра: конфликт → 409.
PATCH требует хотя бы одно поле и запрещает null для обязательных полей.
Удаление проекта каскадно удаляет его аудиты и проблемы в одной операции.
Обращение к удалённым ресурсам → 404.

### 2. Запуск независимого аудита

Создание аудита требует существующий проект. Pydantic discriminated union по
`kind` задаёт два разных входа:

- `code`: исходный текст Python, от 1 до 50 000 символов. Начальные правила:
  синтаксис через AST, вызовы eval/exec, подозрительные литералы секретов,
  слишком длинные функции. Исходный код никогда не выполняется.
- `design`: структурированный список элементов интерфейса, от 1 до 100 элементов:
  тип элемента, текст/accessible name, цвет текста и фона, размер шрифта,
  размеры интерактивной области. Начальные правила: отсутствующие подписи,
  малый текст, низкий контраст, маленькие интерактивные элементы.

Дизайн оценивается только по переданным характеристикам; визуальное качество всей
страницы и реальное удобство пользователя из этих данных определить нельзя.
URL не загружаются, GitHub не сканируется, сторонний AI API не требуется.

Анализаторы — чистые функции: одинаковый вход и версия правил дают одинаковые
результаты. Ошибка синтаксиса анализируемого кода становится finding,
а неверная структура API-запроса → 422. Сначала вычислить все результаты,
затем записать аудит и его findings одной операцией.

Оценка: `max(0, 100 - сумма штрафов)`, штрафы low=5, medium=10, high=20,
critical=30 за finding. Это учебная шкала; формулу показывать в отчёте.
Повторные аудиты разрешены и сохраняют историю.

### 3. Обработка проблем и отчёт

Получить список проблем с фильтрами severity/status, отметить проблему решённой
с непустым комментарием, при необходимости снова открыть её.
Закрытие без комментария → 422, повтор текущего статуса → 409.
При повторном открытии очистить комментарий о решении.

Отчёт содержит исходный балл, числа открытых/закрытых проблем и отдельный
расчётный балл по оставшимся открытым проблемам. Ручное закрытие не доказывает
исправление кода: исходный балл не меняется, подтверждение требует нового аудита.
Если finding не относится к указанному audit_id, вернуть 404.

## План REST API

Все предметные endpoints имеют префикс `/api/v1`.

| Метод | Путь | Результат |
|---|---|---|
| POST | /projects | Создать проект, 201 |
| GET | /projects | Список; search, offset, limit; 200 |
| GET | /projects/{project_id} | Проект, 200 |
| PATCH | /projects/{project_id} | Изменить метаданные, 200 |
| DELETE | /projects/{project_id} | Каскадное удаление, 204 без тела |
| POST | /projects/{project_id}/audits | Провести code/design аудит, 201 |
| GET | /projects/{project_id}/audits | История; kind, offset, limit; 200 |
| GET | /audits/{audit_id} | Детали аудита, 200 |
| GET | /audits/{audit_id}/report | Вычисленный отчёт, 200 |
| GET | /audits/{audit_id}/findings | Проблемы; severity, status, offset, limit; 200 |
| PATCH | /audits/{audit_id}/findings/{finding_id} | Изменить статус, 200 |

Параметры: UUID для идентификаторов, offset >= 0, limit от 1 до 100
(по умолчанию 20). Списки возвращают items, total, offset, limit.
Неизвестные поля запросов запрещены. Для всех endpoints нужны response_model
и документированные ошибки в Swagger.

Доменные ошибки: `{"error": {"code": "...", "message": "..."}}`.
Ошибки входных данных сохраняют стандартный формат FastAPI `detail` с полями ошибок.

## Хранилище и изоляция

Три типизированных словаря UUID → модель внутри MemoryStore. Store создаётся
в create_app и помещается в app.state. Через Depends сервисы получают один store
данного приложения; тестовые приложения получают независимые store.
Проверки уникальности и связанные записи защищаются общей блокировкой.
Не возвращать изменяемые объекты хранилища без копирования.

## Границы задания

В первой версии не нужны база данных, авторизация, frontend, фоновые очереди,
загрузка репозиториев или AI-интеграции. Следующий шаг — согласовать Pydantic
контракты и реализовать первый сценарий, затем аудит и обработку findings.
Перед сдачей реализовать все маршруты, пройти Swagger checklist, зафиксировать
версии зависимостей после проверки и загрузить проект в общий Git-репозиторий.
